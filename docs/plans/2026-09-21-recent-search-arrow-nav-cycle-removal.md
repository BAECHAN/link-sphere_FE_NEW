# 데스크톱 최근검색 드롭다운 — 화살표 키 순환 제거 + 스크롤 추적

## Context

방금 배포된 데스크톱 최근검색 드롭다운(PR #165)을 실제로 써보니 화살표 키 동작이
직관과 어긋난다는 피드백을 받았다:

1. "모두지우기있는곳에서는 arrow up하면 검색창으로 가야되지않을까" — 현재는
   "모두 지우기"에서 ↑를 누르면 마지막 검색어로 순환(wrap)한다
   (`NavbarSearch.tsx:179-192`의 `(activeRow - 1 + totalRows) % totalRows`).
2. "맨아래로 되돌아가는 순환구조인것도 마음에 안듦" — ↓/↑ 모두 모듈로 연산으로
   끝에서 반대쪽 끝으로 순환한다. 이 순환 자체가 불편하다는 지적.
3. "검색영역에서는 메인스크롤안되도록해야" + 후속 메시지 "5개 이상될때 화살표로
   조작시 화면안보이는 영역에 있을경우 스크롤도 따라가야한다" — 화살표로 이동한
   활성 항목이 드롭다운의 스크롤 영역(`max-h-[190px]`) 밖에 있으면 그 목록이
   따라 스크롤돼야 한다.

사용자 확인(대화 중):

- 배경(메인) 페이지 스크롤 잠금은 필요 없음 — 화살표 내비게이션이 **드롭다운 내부
  스크롤만** 따라가면 충분하다.
- 입력창에서 ↓ 첫 클릭은 지금처럼 "모두 지우기"를 건너뛰고 바로 첫 검색어로 간다
  (가장 흔한 동작이 한 번에 닿아야 하므로 유지).

## 결정 — 순환 없는 선형 구조로 전환

시각적 레이아웃(입력창 → "모두 지우기" 헤더 → 검색어 목록)과 논리적 순환 순서가
어긋나 있던 것이 근본 원인이었다. "모두 지우기"를 목록의 *논리적 마지막*이 아니라
_논리적 첫 자리_(시각적으로도 입력창 바로 아래)로 재정의해, 순환 없는 일직선
구조로 바꾼다:

```
입력창 ↔ 모두 지우기 ↔ 검색어1 ↔ 검색어2 ↔ ... ↔ 마지막 검색어
```

| 위치                       | ↓                                         | ↑                                                 |
| -------------------------- | ----------------------------------------- | ------------------------------------------------- |
| 입력창(아무것도 활성 아님) | 검색어1로(모두지우기 건너뜀, 지름길 유지) | 모두 지우기로                                     |
| 모두 지우기                | 검색어1로                                 | **입력창으로 나감(activeRow=null)** ← 요청 1 수정 |
| 검색어1(첫 항목)           | 검색어2로                                 | 모두 지우기로(기존과 동일, 변화 없음)             |
| 검색어 중간                | 다음 항목                                 | 이전 항목                                         |
| 마지막 검색어              | **그대로 멈춤(순환 없음)** ← 요청 2 수정  | 이전 항목                                         |

좌/우(검색어 셀 ↔ 삭제 셀)도 같은 이유로 행을 넘나들며 순환하던 것을 제거하고,
같은 행 안에서만 경계에 닿으면 멈추도록 단순화한다("모두 지우기" 행은 셀이 1개라
좌우 이동 자체가 없음).

## 구현

**`src/widgets/layout/navbar/ui/NavbarSearch.tsx`** — `handleKeyDown`의 `ArrowDown`/
`ArrowUp`/`ArrowLeft`/`ArrowRight` 블록(당시 164-220줄)을 위 표대로 다시 쓴다.
`totalRows`와 모듈로 연산, `ArrowLeft`/`ArrowRight`가 쓰던 `cells` 평면 배열(당시
203-219줄)을 전부 제거한다 — 행간 이동이 없으므로 필요 없다. `Escape`(141-155줄)·
`Enter`(222-241줄) 블록은 그대로 둔다.

**`src/widgets/layout/navbar/ui/RecentSearchDropdown.tsx`** — `activeRow`/`activeCol`이
바뀔 때 해당 셀을 드롭다운 자체의 스크롤 컨테이너 안으로 스크롤한다:

```tsx
useEffect(() => {
  if (activeRow === null) {
    return;
  }

  const id = getRecentSearchCellId(activeRow, activeCol);
  document.getElementById(id)?.scrollIntoView({ block: 'nearest' });
}, [activeRow, activeCol]);
```

`scrollIntoView({ block: 'nearest' })`는 대상이 이미 보이는 조상에는 아무 영향을
주지 않고, 안 보이는 가장 가까운 스크롤 컨테이너만 최소한으로 스크롤한다. 이 그리드
바깥에서 실제로 스크롤 가능한 조상은 행 목록 rowgroup(`overflow-y-auto
max-h-[190px]`) 하나뿐이고 — `nav`는 `sticky`(스크롤 컨테이너 아님), 드롭다운
전체는 항상 뷰포트 상단 인근(sticky nav 안)에 있어 실질적으로 `window`가
스크롤될 일이 없다 — 그래서 별도 조치 없이도 배경(메인) 페이지는 건드리지
않는다(사용자 확인 사항). 항목 수가 적어(≤4개, 190px 안에 다 들어감) 스크롤 자체가
필요 없을 때는 `scrollIntoView`가 자연히 no-op이므로 "5개 이상"을 코드로 따로
분기하지 않는다.

## 테스트 (`NavbarSearch.test.tsx`)

기존 케이스 중 순환 전제로 작성된 것 1개를 교체하고, 새 경계 동작 2개 + 스크롤
추적 1개를 추가한다.

- **교체**: "↓를 검색어 개수만큼 누르면 '모두 지우기' 행에 도달하고 Enter로
  전체 삭제된다" → ↑로 그 자리에 도달하는 것으로 바꾼다.
- **추가**: "모두 지우기에서 ↑를 누르면 입력창으로 나간다".
- **추가**: "마지막 검색어에서 ↓를 눌러도 더 내려가지 않는다".
- **추가**: "화살표로 이동하면 활성 셀이 스크롤 컨테이너 안으로 스크롤된다" —
  `src/test/setup.ts:66`에 전역 스텁된 `Element.prototype.scrollIntoView`이
  호출됐는지만 확인한다.
