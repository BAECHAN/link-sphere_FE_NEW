# 비밀번호 칸 붙여넣기·표시 버튼 정책 — 지금 동작을 유지하는 근거를 AUTH.md에 기록

> 비밀번호 칸(확인 칸 포함)의 붙여넣기를 막지 않고 눈(표시) 버튼도 유지하기로 하고, 그 근거를 `docs/AUTH.md` §8-G에 남긴다. 코드 변경 없음.

## Context

- 사용자 질문(2026-11-02): 비밀번호·비밀번호 확인·탈퇴 비밀번호 칸에서 복사·붙여넣기를 막을 수 있는가, 업계 표준은 무엇인가.
- 사용자 고민: 비밀번호 칸은 붙여넣기를 허용해도 되지만, **확인 칸**은 막아야 하지 않을까(첫 칸의 오타가 확인 칸으로 번지는 걱정).
- 조사한 사실:
  - 비밀번호 칸은 5개 폼에 9칸(로그인 1·가입 2·재설정 2·변경 3·탈퇴 1)이고, 모두 `FormInputPassword` → `src/shared/ui/elements/PasswordInput.tsx`를 거친다. `onPaste`·`onCopy`·`autoComplete`는 하나도 없다.
  - 표준은 붙여넣기 허용 쪽이다. 근거: NIST SP 800-63B-4 §3.1.1.2, OWASP Authentication Cheat Sheet, WCAG 2.2 SC 3.3.8(로그인·탈퇴 같은 인증 칸), GOV.UK Passwords 패턴.
  - 가려진 칸의 복사는 브라우저가 이미 막는다. 근거: Chromium `editor.cc`의 `Editor::CanCopy()`, Firefox `TextEditor.cpp`의 `IsCopyToClipboardAllowedInternal()`(main 브랜치 소스).
  - 직접 측정(Chrome 154, example.com에 만든 빈 테스트 칸): 가려진 칸에서 `⌘A`·`⌘C` 후 다른 칸에 `⌘V` → copy 이벤트 0회, 붙은 값은 이전 클립보드 내용이었다. Safari는 확인하지 못했다.
  - 눈 버튼을 누르면 칸이 `type="text"`(`PasswordInput.tsx:12`)로 바뀌어 복사가 된다.
- 결정(사용자 선택): **막지 않음 + 근거 기록**.
- 이어진 질문: 경로 ③을 막으려고 눈 버튼을 지워 `type=password`로 고정해야 하나. 조사한 사실은 다음과 같다.
  - NIST §3.1.1.2는 입력 중 비밀번호를 표시하는 선택지를 제공하라고 권고한다(SHOULD).
  - GOV.UK Password input 컴포넌트는 표시·숨김 버튼을 기본으로 두고, 그래서 확인 칸이 필요 없다고 쓴다.
  - NN/g Nielsen(2009)은 가리면 오류가 는다고 썼다. 반대 근거로, Georgia Tech 연구 페이지가 소개하는 2024년 ACM CCS 연구는 가림 여부가 입력 시간·오타에 유의미한 차이를 내지 않았고 토글 사용도 드물었다고 보고한다.
  - Edge는 브라우저 자체 "암호 표시" 버튼을 기본으로 띄우고(Microsoft `PasswordRevealEnabled` 정책 문서), Chromium `CanCopy()`는 보이게 한 칸의 복사를 허용한다. 그래서 우리 버튼을 지워도 Edge에서는 ③이 남는다. 이 레포는 `::-ms-reveal`을 숨기지 않는다.
- 결정(사용자 선택): **눈 버튼 유지 + 근거 기록**.

## 실행 순서

1. `git log origin/main..main`으로 미푸시 커밋 확인 → `EnterWorktree` → `cp ../../../.env .` · `pnpm install`
