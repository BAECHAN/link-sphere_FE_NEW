2026-09-28, 다른 세션에서 계획 문서 구조를 바꿔달라는 요청(PR #220,
`docs/plans/2026-09-28-auth-hardening.md`)이 마음에 든다는 피드백을 계기로
표준화했다. 처음엔 그 세션의 번호 체계(0/1/2)를 그대로 쓰려 했으나, "그때만
잘 읽혔던 거지 모든 상황에 맞으리란 보장은 없다"는 지적으로 업계 조사를
다시 했다. 그 결과 **Rust RFC 계열**(Ember·Yarn·React·Vue가 각자 README에서
Rust/Ember RFC 절차에서 영감을 받았다고 밝힘 — [Ember](https://github.com/emberjs/rfcs),
[React](https://github.com/reactjs/rfcs), [Vue](https://github.com/vuejs/rfcs))만이
여러 독립 조직이 같이 쓰는 사실상 표준임을 확인했다. 이 skill의 골격은 그
공통 뼈대(Summary → Motivation → Detailed design → Drawbacks → Alternatives →
Unresolved questions)를 이 레포 용어로 옮긴 것이다.

## 공통 골격

```
# 제목
> Summary (한 줄 요약, 선택)

## Context (Motivation)         ← 왜 이 변경이 필요한가 · 지금 상황 · 사전 조사
## 판단이 필요했던 항목 (Alternatives·Drawbacks)
                                ← 항목 | 결정 | 근거·기각한 대안 표
## 세부 계획 (Detailed design)   ← 위치 | 변경 내용 표
## 영향 범위 (§5)
## 검증 방법
## 남은 것 (Unresolved questions)
```

`Context`가 하네스가 요구하는 Context, `세부 계획`의 "위치" 열이 핵심 파일 목록,
`검증 방법`이 하네스가 요구하는 검증 섹션을 각각 충족한다. Mermaid 다이어그램
(§12)은 `Context`나 `세부 계획`의 각 하위 절 첫머리에 둔다 — 별도 규칙 아님,
§12 그대로 적용.

## Full vs Minimal

아래 중 **하나라도** 해당하면 Full, 아니면 Minimal.

- PR이 2개 이상
- 레포가 2개 이상 (FE+BE 등)
- 데이터 계약(스키마·DTO·API 응답 형태) 변경

| 절                    | Minimal                                | Full                                      |
| --------------------- | -------------------------------------- | ----------------------------------------- |
| Context               | 필수                                   | 필수                                      |
| 판단이 필요했던 항목  | 결정 표 하나(판단 없으면 "없음" 한 줄) | 결정 표 + 뒤집힌 전제 + 위험 관리         |
| 세부 계획             | 표 하나                                | 레포별(FE/BE) 또는 Phase별로 나눈 여러 표 |
| 영향 범위 / 검증 방법 | 필수                                   | 필수                                      |
| 남은 것               | 있을 때만                              | 필수                                      |

섹션 자체는 Minimal에서도 그대로 유지한다 — 통째로 빼면 "일부러 뺀 건지
빠뜨린 건지" 구분이 안 된다.

## 성격별 모듈 (3개)

| 모듈           | 위치                                                          | 내용                                                                    |
| -------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 버그 조사      | `Context` 안에 `### 가설` / `### 재현 절차` / `### 근본 원인` | 원인을 확정하는 계획은 "현재 상황을 조사하는" 내용이라 Context에 속한다 |
| 시각 변경 시안 | `판단이 필요했던 항목`에 `### 시안 후보` (§9, 반영 전 승인)   | 후보 비교는 판단이므로 이 절                                            |
| 다단계         | `세부 계획` 안에 `### Phase N`                                | PR 단위든 Phase 단위든 세부 계획 하위                                   |

**나머지는 모듈이 아니라 골격 규칙으로 흡수한다**:

- 크로스레포 → `세부 계획`을 레포별(예: 백엔드/프론트엔드)로 나눈다
- 개명·리네이밍 → `세부 계획` 표 열을 `위치 | 기존 | 신규`로 바꾼다
- 규칙·프로세스 선례 → `판단이 필요했던 항목` 표의 "근거" 열에 적는다(선례가
  3개 이상이면 그 절에 `### 근거 선례`를 따로 둔다)

## 판단 vs 변경사항 분리 (핵심 원칙)

**"왜 · 대신 · 했으나"가 들어가는 문장은 `판단이 필요했던 항목`에 쓰고,
`세부 계획` 표 셀에는 무엇을 어디서 바꾸는지만 쓴다.** 이는 RFC 계열의
Alternatives/Drawbacks 대 Detailed design 구분과 같은 것이다. 근거가 필요하면
`세부 계획` 셀에서 `판단이 필요했던 항목`의 결정 이름을 참조한다.

- `판단이 필요했던 항목` 표 열: `항목 | 결정 | 근거·기각한 대안`
- `판단이 필요했던 항목`의 뒤집힌 전제 표 열: `발견 | 그래서 바뀐 것`
- `세부 계획` 표 열: `위치(경로:줄, 신규는 "(신규)") | 변경 내용`. 문구만
  바뀌면 `변경 전 | 변경 후`로 바꿔도 된다.
